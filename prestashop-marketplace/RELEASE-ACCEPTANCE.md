# PrestaShop — acceptance and release handoff (#1807)

This document is a release procedure, not a release authorization. The live evidence ledger and remaining checklist are in Convor-IO/Convor #1807. All three feature branches use `feat/prestashop-finalization-1807`. Do not infer that a local candidate is deployed, approved by Marketplace, or ready for Advanced.

## A. Freeze a common candidate

- Coordinate with #1806 (WordPress) and #1802 (native commerce). Use one widget/bootstrap, installation observation and pairing implementation. Resolve shared widget changes on a reviewed common baseline. Do not restore the older standalone WordPress card on top of the shared card. The observation service from WP commit 70535b3b55 was ported into the shared routes/card in SaaS 267dcf0015.
- Record Plugins, SaaS and Website full SHAs, exact `convor.zip` SHA-256, pinned PS image versions, actual PHP versions, test environment and gate exit codes. Freeze this tuple before reviewer submission. A code change invalidates the corresponding earlier artifact evidence.
- Stable and versioned Website downloads must be byte-identical to the tested module, with independent filename-correct SHA-256 sidecars. Verify the downloaded content as well as the local ZIP. Never package fixture overrides, local QA keys, identity secrets, tests or reviewer credentials.

## B. Local acceptance

Use the existing isolated fixture and setup instructions in `integration-tests/fixtures/prestashop/README.md`. Never point these commands at a merchant installation.

1. Plugins: run `pnpm gate` and the deterministic package test; build the candidate with `python3 scripts/build-prestashop.py`. Compare the resulting hash and both Website aliases.
2. Run `integration-tests/fixtures/prestashop/run-matrix.sh` against all four actual shops, with real isolated SaaS and widget assets. Do not mock successful conversations. Retain the results for API pairing/replay, actual dashboard pairing, manual/theme installation, identity and logout, signing-secret rotation/audit redaction, product/cart, and blocked-CDN checkout. Verify every installed ZIP member with `verify-installed-archive.py`, not just the main PHP file.
3. Run the targeted lifecycle, multistore, BO ACL, pairing-policy, cross-tab, child-theme, order/currency, reverse-proxy and conflict tests listed in #1807. Run `test-pairing-mfa.mjs` with a fresh synthetic account and `test-cookieconsent.mjs` with the pinned self-hosted CookieConsent 3.3.0 package as documented in the fixture README. Run `test-installation-observation.mjs` against the local API/dashboard; observed activity is diagnostic, not proof of domain ownership.
4. Debug diagnostics: `bash integration-tests/fixtures/prestashop/test-debug.sh` preserves real E_ALL; `PRESTASHOP_DEBUG_LOG_ONLY=1` additionally logs rather than displays upstream PHP diagnostics so cart JSON can be parsed. The initial apparent empty checkout on PS9.0.3 was the native debug canonical-redirect notice, not a missing template. The corrected harness follows its real same-origin link and requires HTTP 200 plus visible checkout. A fresh 9.0.3 fixture with no Convor ever installed independently reproduces raw E_ALL non-JSON cart and log-only HTTP 400. The bundled, unconfigured native `psshipping` 2.0.9 causes HTTP 400 even with Convor disabled and also in production mode. Disabling only that optional provider through the native module command in the disposable 9.0.3 fixture yields HTTP 200, all four checkout steps, and PASS for the normal checkout and all four actual E_ALL log-only Convor tests. Restore the original shipping module state afterwards. `run-matrix.sh` applies the same verified fixture isolation. Reproduce the original native failure with `PRESTASHOP_DEBUG_LOG_ONLY=1 PRESTASHOP_DEBUG_BASELINE=1 PRESTASHOP_DEBUG_GREP='native checkout debug baseline' bash integration-tests/fixtures/prestashop/test-debug.sh`; reproduce the corrected standard checkout with `PRESTASHOP_DISABLE_BUNDLED_SHIPPING=1 PRESTASHOP_DEBUG_LOG_ONLY=1 bash integration-tests/fixtures/prestashop/test-debug.sh`. Raw displayed E_ALL still breaks native cart JSON with Convor absent even after isolating psshipping; the verified log-only mode keeps E_ALL enabled without injecting diagnostics into responses. This does not certify psshipping compatibility or require merchants to disable carriers. Do not count a visible form on HTTP 400 as PASS.
5. SaaS: prepare the isolated seeded test database and run the repository's canonical gate. Website: initialize the pinned api-spec submodule; run its canonical gate, production guide render, mobile/keyboard and exact ZIP download tests. Verify the PL/EN PDF contents and regenerated reviewer manifest against the frozen artifact. See #1807 for individual session/commit references.
6. Run the exact final integrated candidate through required repository CI according to each repository's AGENTS instructions. Only authorized master promotion can create the production release. Local gates and preview URLs are not CI/deployment evidence. The existing Plugins GitHub-hosted CI runs the hermetic gate and deterministic archive build. The cross-repository real-stack release job is implemented in the private SaaS repository as a manually dispatched GitHub-hosted four-version matrix. It checks out the exact published public Plugins commit, validates the exact direct ZIP SHA and provisions an isolated synthetic SaaS on each runner. The existing private API-spec/package access is reused in the SaaS repository; no production host or new runner registration. The workflow must actually execute successfully after publication; local syntax validation is not a CI result. Do not install a runner, give a token repository access, or run fixed fixture ports against shared production services to fabricate this check. The local real-stack matrix is mandatory evidence until the dedicated job is provisioned; CI enforcement remains open.

## D. Publication sequence (after explicit authorization)

1. Confirm seller eligibility, legal terms and actual product identity/module_key. The technical checklist explicitly lists MIT as compatible but the Partners Help Center requires AFL; obtain a definitive answer before changing distribution terms. Build the Marketplace-only candidate with `scripts/build-prestashop-marketplace.py --guides prestashop-marketplace/seller-guides --module-key-file <issued-key-file>` from the verified direct archive. A keyless preflight build already supports local checks but is not a submission. Run official validator. Save the exact report and remediation evidence; retest whenever contents change. Use the current portal's actual instructions rather than invented fields or requirements.
2. Prepare bilingual listing and reviewed screenshots/PDFs. Provide reviewer access only to an isolated, expiring demo. Do not embed credentials in the package, screenshots, PDF, issue or support messages.
3. Submit once the technical/commercial requirements are confirmed. Record submission ID, exact artifact hash, time and review state. Track rejection/feedback; fix the issue with a regression test and revalidate the new artifact.
4. Promote the reviewed integrated release using the repository delivery procedure, verify CI and public deployment. Verify HTTPS downloads, exact checksum, trial proof/revoke and a real two-way conversation on the approved public shop. Roll back to the last known-good tested candidate if the widget breaks storefront checkout, identity isolation or core chat.

## E. Support and monitoring

The operational triage, actual existing support contacts, sanitized GitHub issue template and published artifact smoke are documented in `SUPPORT.md`. The local public QA security/TLS smoke is executable without production credentials. The published artifact workflow must be dispatched after release and verified; contractual staffing/response targets remain subject to the actual seller agreement.

Assign a responsible human owner and contractual coverage before listing. Do not promise a response/repair SLA that has not been accepted. Maintain a single integration issue template: PS/PHP/module version, theme and child-theme, install method, domain/consent mode, redacted browser error/status, minimal reproduction and whether the problem reproduces with the module disabled. Never request shop admin passwords, private Convor API keys, signing secrets, visitor handles, raw carts or customer data in ordinary tickets.

Triage: checkout disruption, cross-tenant exposure and credential handling are release blockers (disable the module or stop rollout; notify security/engineering). Pairing, invalid domain and missing widget: inspect actual site scope, key binding, allowed domain, CMP and network, then verify a conversation in both directions. Module/ZIP problems: verify archive hash, supported version, upload/uninstall and cache. Third-party CMP/checkout issues: reproduce with the extension and native baseline, document supported versions. Monitor approved deployment health, downloadable artifact identity, authentication/installation error rates, and real synthetic two-way smoke; report only aggregated counts or synthetic evidence. Capture a red→green test before shipping fixes.

Release acceptance is complete only when the exact artifact and integrated baseline are verified and the approved external steps are recorded in #1807. Until then distinguish the local candidate, upstream fixture limitations, Advanced dependency and seller/publication blockers.

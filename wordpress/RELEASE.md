# WordPress.org release

1. Run the repository gate, the real WordPress/WooCommerce fixture, the two-way chat and theme snippet tests against the matching Convor release, and Plugin Check. Confirm the minimum and newest supported WordPress/PHP versions with actual test results. Update Tested up to in readme.txt only to the highest verified WordPress version.
2. Confirm the intended WordPress.org account and slug, contributor usernames, service URLs, GPL license, privacy disclosure and directory assets. Do not publish a directory link before the listing is approved. Use the release artwork in the repository's `wordpress-directory-assets/` (existing Convor brand logo and real QA screenshots); copy these to the SVN assets directory, not the runtime ZIP. Confirm the approved name, trademark use and screenshot captions before submission.
3. Run `python3 scripts/build-wordpress.py`. Verify the ZIP contents and SHA-256; install this exact ZIP on a clean site for the final smoke test. Copy the versioned archive and checksum into the Website repository `public/downloads/wordpress/` and keep both guide links and `wordpress-download.test.ts` aligned. Verify the same SHA-256 in both repos. This is the fallback direct download, not a WordPress.org listing. Deploy and verify the compatible SaaS pairing/status endpoints and matching CDN widget before the Website release that exposes the ZIP. The WooCommerce context integration requires the instance handle's public widget key; on older CDN builds it intentionally sends no context rather than targeting the wrong widget.
4. Submit the tested ZIP at https://wordpress.org/plugins/developers/add/. External review and approved directory credentials are required.
5. After approval, check out the assigned SVN repository. Copy the runtime contents (not the enclosing convor directory) into trunk, copy the same files into tags/<version>, and copy approved artwork to assets. Verify trunk and tag readmes, version consistency and translations. Review SVN status and diff before committing with authorized credentials.
6. Verify the public listing, ZIP download, install/activate/update flow, fresh install, support forum and links. Test rollback to the previous release if an update is required.

## Release operation and support

- Before submission, assign an organization-controlled WordPress.org owner, a support forum maintainer, and a security/release contact. Enable 2FA and release confirmation. Keep SVN credentials in the approved secrets manager, never in the ZIP or public issue.
- Record the tested SaaS, CDN, plugin and Website commit IDs, version, checksums, fixture/browser results, directory review receipt and deployment order in the release issue.
- Investigate pairing failures using domain/project configuration, grant expiry, and replay protection. For widget failures, check the published CDN and allowed origin, clear site/CDN caches and run the two-way chat smoke test. For WooCommerce, check consent, exact instance identity and Store API access. Do not ask customers for public issue attachments containing credentials, visitor identifiers or chat content.
- If a release is defective, stop further distribution and verify a known-good SaaS/CDN and plugin combination in staging. Do not overwrite an immutable SVN tag or silently downgrade installations. Prepare a versioned hotfix, repeat the release gates and obtain approval. A merchant can disable the widget locally without losing stored conversations.
- After publication, monitor the directory support forum and existing SaaS operational alerts. Repeat the real installation, chat, consent and cart fixture tests against supported WordPress/PHP and current WooCommerce updates. Do not introduce separate hidden telemetry.

Release workflow artifacts are candidates, not published versions. No workflow uploads to WordPress.org automatically. If the SaaS pairing endpoint is not deployed yet, do not release the paired installation as available.
